01 · Two frontend environments

Studio serves production at scale; Epichan tests Agent-first development on real product work.

02 · Copilot message orchestration

A user message moves through session, orchestration, model, and tool loops before streaming back to the frontend.

The frontend does not make one model call and wait for a complete answer. It first obtains user configuration and feature flags, then sends the message over a long-lived connection. The backend represents the request as a Turn; the Orchestrator selects an execution path; and the Responder loops between model inference and tool execution before safety, citation, and protocol processing stream the result back.

03 · Copilot production delivery

Build, release, and feature activation are three independently controllable stages.

Copilot delivery does not depend on a single full cutover. Content hashes make frontend artifacts immutable; the same verified artifacts are promoted from pre-production to production; regions and users receive them progressively; and Feature Flags or a Kill Switch separate code deployment from feature activation.

ARTIFACT

Release what was tested

Content-addressed static resources are not overwritten in place. Production promotion reuses the verified build, reducing differences introduced by rebuilding.

ROLLOUT

Use time to limit the blast radius

Exposure expands by stage and region while automated checks and health signals track the change. A problem can stop subsequent stages.

RUNTIME

Deployment does not mean immediate activation

Feature Flags support experiments and gradual enablement. A Kill Switch can disable a high-risk capability without another deployment.

RECOVERY

Prepare recovery paths before release

Rollback, feature shutdown, and regional traffic adjustment address different failure scopes. The response follows the layer where the fault appears rather than one universal redeployment.

05 · Epichan Harness and Loop

The Harness governs how one task executes; Loop Engineering governs how the delivery system keeps improving.

Epichan is more than another Copilot frontend repository. Bebop Lite provides a real product and proving ground. The Harness organizes tasks, roles, permissions, state, and evidence into a reliable execution kernel. The Loop connects intake, quality verification, real delivery, feedback, and later validation.

Product Surface

Bebop Lite provides a real engineering environment

Agents modify product code with shared components, architectural constraints, performance requirements, and real backend connections, so their output must meet normal software-delivery standards.

Harness Engineering

Make one execution schedulable and recoverable

A task has persistent state, roles, a claim, execution records, and check conditions. If an Agent fails or hands off, the system still knows what was completed and who acts next.

Loop Engineering

Feed evidence and failure into the next cycle

Post-delivery traces, evaluations, and reports are classified into product tasks, Skills, deterministic checks, or Harness improvements, then validated on later comparable tasks.

06 · Task lifecycle

Tasks advance through explicit states; semantic judgment, system facts, and risk ownership belong to different roles.

A human request is not simply picked up and executed. The Task Engine records current state, execution ownership, and evidence. Developer, Reviewer, and Judge roles handle different stages; CI and reconciliation provide deterministic facts; humans handle exceptions and risk decisions when required.

07 · Representative requirement

Adding a copy action to chat messages: how an ordinary feature traverses the full Loop.

This common frontend requirement illustrates how Epichan works: add a copy action beneath Assistant messages and support both desktop and mobile. It is a mechanism example, used to show how the stages collaborate.

The requirement becomes more than code—it becomes a verifiable delivery outcome

Each stage leaves state and evidence that the next role can independently inspect.

REPRESENTATIVE FLOW
Intake

The task describes user behavior, interaction placement, desktop and mobile requirements, and feedback for copy success and failure.

Implement

The Developer Agent locates the shared message component and design-system capability, implements behavior and state handling, runs tests, and submits a PR.

Verify

Type checking, unit tests, lint, and architecture rules cover deterministic requirements; the Reviewer then examines component reuse, interaction behavior, and edge cases.

Judge

The Judge evaluates the PR, test results, and desktop/mobile screenshots against the acceptance criteria. Missing evidence or incorrect behavior returns the task for revision.

Deliver

After every check passes, the task becomes ready to merge. The internal task records actual delivery only after GitHub confirms the PR was merged.

Improve

If multiple surfaces repeatedly implement the same action, the team can write back a shared-component rule or check, then observe whether later tasks reuse the common implementation.

09 · Engineering takeaways

Four lessons from production AI and the Agentic Loop.

01

Autonomous execution starts by making work a durable task

Only when a requirement becomes persistent, queryable, claimable, and recoverable can the system manage unsupervised Agent work instead of depending on one chat session.

02

A model's self-report cannot replace acceptance evidence

Deterministic tests, architecture checks, independent review, and inspectable outputs must enter the execution graph. An Agent cannot advance state merely by saying the task is complete.

03

Internal state cannot replace external delivery facts

The Task Engine records execution progress, but systems such as GitHub still own PR, CI, and actual merge state. The two domains require continuous reconciliation.

04

A write-back still needs later validation

Fixing one task or adding a Skill or rule does not prove the system improved. The evidence and outcomes of later comparable tasks determine whether the loop is effective.
