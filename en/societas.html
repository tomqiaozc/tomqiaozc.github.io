01 · Product and system

From answering once to completing an entire piece of work.

A user provides a real work objective. The system decomposes the task, invokes models and tools, handles code and files in an isolated environment, operates a browser when necessary, checks the result, and delivers an editable document, presentation, analysis, or webpage. Successful work can become a reusable capability for later tasks.

03 · Simplified architecture

Conventional APIs accept requests; the Agent Runtime owns uncertain, long-running execution.

At a public level, Societas can be understood as two runtime boundaries. The API layer handles identity, task entry, and state queries. The Agent Runtime handles model inference, plan progression, tool execution, and artifact generation. Separating them enables independent scaling, deployment, and recovery for short requests and long-running work.

Agent plans / calls tools

Execution plane

The model decides; the backend executes under control

The model emits plans and structured tool calls. The backend validates parameters, authorization, and call state before running research, code, file, or browser tools and returning results for continued inference.

State and messaging

Business facts, process state, and live delivery have separate roles

Structured business data goes to databases and files or final artifacts to object storage. Redis holds cache and short-lived process state; reliable messaging carries ordered live events for long-running tasks.

Security and observability

Do not trust model output or assume the internal network is safe

Generated code runs in an isolated sandbox, sensitive data uses user-level encryption, and service communication uses TLS. Logs, metrics, and traces span model, tool, messaging, and storage calls.

Why this structure matters: one Agent run may last several minutes and cross multiple external dependencies. A browser connection or one service process cannot be the source of truth; progress, messages, and final artifacts must live inside recoverable boundaries.

05 · Engineering case one

Migrating a tool protocol is not replacing one parser.

Tool calling is the Agent Runtime's main loop: the model requests a call, the backend validates and executes it, and the result returns to context. The old approach depended on convention-formatted model text and was vulnerable to format drift. Native structured calls are more reliable, but migration touches message protocols, streaming events, sub-Agents, and multi-model compatibility at once.

Use dual mode to turn a high-risk cutover into an observable, reversible evolution

The two protocols coexist under control inside the same runtime instead of switching at once.

LED / PRIMARY DEVELOPER
Problem

Structured calls use different message blocks and streaming events across model SDKs. Once the main Agent changes, sub-Agents, result injection, and conversation history must stay on the same protocol.

Design

Retain the old protocol as fallback, select mode through configuration, expose the same tools through either protocol, propagate mode to sub-Agents, and adapt streaming aggregation and result pairing.

Correctness

Validate tool name, call ID, and argument completeness before execution. Incomplete streamed calls cannot produce side effects, preventing partial JSON from contaminating later context.

Release

Runtime metrics record call mode and failure type; limited enablement, comparison, and fast rollback replace a one-time global migration.

Engineering judgment

Protocol risk exists not only in the producer but in every consumer and historical record. Completion means the main Agent, sub-Agents, executor, message history, and observability all understand the same protocol version.

06 · Engineering case two

Upgrade “the message exists” to “the live stream recovers automatically.”

Long-running Agent tasks last minutes and produce many ordered events. The old design stored history fragments in Redis Lists but used Redis Pub/Sub for live delivery. Messages did not wait for a temporarily disconnected subscriber, so users had to refresh and replay history.

Stores short-term history for refresh and reconnect replay.

Reliable live layerService Bus Session

Retains unacknowledged messages with ack, redelivery, and per-session FIFO.

Architecture judgment

The problem is delivery semantics, not retry count

Retry wrappers cannot turn Pub/Sub broadcast semantics into offline retention. The fix must redefine which layer owns real-time reliability.

Migration control

Abstract transport and retain rollout and rollback

A shared MessageTransport interface isolates business code so old and new transports can switch by configuration without spreading infrastructure migration across callers.

Concurrency failure

Resource lifecycles must follow failure boundaries

Shared send resources affected one another under concurrency. The fix separated resources by channel, coordinated concurrent creation, locked use, and rebuilt only the failed entry.

Honest boundary

At-least-once is not exactly-once

The queue may redeliver. Display messages and side-effecting tool execution still need business-level idempotency keys and state machines.

07 · Engineering case three

Make the Agent safe to integrate while protecting user data.

A production Agent must be callable by external products while handling user files and sensitive data. Interfaces, identity, task state, encryption at rest, and transport security need one continuous boundary rather than isolated features.

A / Agent Proxy

Wrap long-running work in a recoverable asynchronous API

Callers establish application identity and API permissions through Client Credentials and App Roles, with request-signature validation protecting API calls. Agent Proxy isolates task data by caller and caller-provided external user, while persistent state allows in-flight work to recover after a restart.

  • Designed independently from scratch and delivered to production
  • Application-level secure access, task isolation, persistence, and recovery
  • Containerization and CI/CD for independent release and maintenance
B / User Encryption

Design lookup, key isolation, and rotation together

A stable hash supports lookup while original identity and user data remain encrypted. Layered keys limit exposure, and self-describing ciphertext allows old and new keys to coexist during progressive migration.

  • Owned system architecture and protocol design
  • Teams integrated data layers through one contract
  • Sharing separates authorization identity from decryption identity
C / Service TLS

Eliminate plaintext communication between service nodes

Delivered runtime certificate injection, format conversion, server-side HTTPS, client CA verification, and multi-environment migration. The accurate boundary is one-way TLS engineering integration—not implementing TLS itself or mTLS.

  • Independently delivered integration and deployment migration
  • Private keys stay out of code and images
  • Leaves room for stronger service identity verification
08 · Engineering judgment

Four engineering lessons from this work.

01

Define delivery semantics before selecting infrastructure

Reliable-messaging choices are not a simple Redis-versus-Service-Bus performance comparison. The deciding requirements are offline retention, ordering, acknowledgment, and redelivery for long-running tasks.

02

Keep observation, gradual rollout, and rollback in production migrations

Native Tool Call used dual-mode compatibility across protocols; message delivery used one interface across transports. Both retained runtime metrics, staged enablement, and configuration rollback.

03

Model the visitor, data owner, and decryption identity separately

In public sharing, a visitor passing authorization does not mean the visitor's own key can decrypt the owner's data. The system first verifies access, then decrypts within a controlled scope using the owner's encryption context.

04

Independent delivery includes development, deployment, and operation

Agent Proxy includes more than API code: authentication, persistent task state, restart recovery, containerization, CI/CD, and observability make it independently deployable and maintainable.
