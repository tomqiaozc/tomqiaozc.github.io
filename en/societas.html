01 · Product and system

From answering once to completing an entire piece of work.

A user provides a real work objective. The system decomposes the task, invokes models and tools, handles code and files in an isolated environment, operates a browser when necessary, checks the result, and delivers an editable document, presentation, analysis, or webpage. Successful work can become a reusable capability for later tasks.

01Understand the objective

Clarify the deliverable, audience, and quality bar.

02Plan and execute

Coordinate models, tools, sub-Agents, sandboxes, and browsers.

03Check and recover

Record state and handle failures, retries, and reconnects.

04Deliver and reuse

Produce editable outputs and retain stable steps.

System-design scope: beyond model inference, a long-running task crosses tools, sandboxes, messaging systems, and clients, so it needs corresponding recovery, observability, and execution-control mechanisms.

03 · Simplified architecture

Ordinary APIs take requests; the Agent Runtime absorbs uncertain long-running execution.

Publicly, Office Agent can be understood as two runtime boundaries: the API layer handles identity, task entry, and state queries; the Agent Runtime handles model inference, planning, tool execution, and artifact generation. Separating them lets each scale, release, and recover independently for short requests and long-running tasks.

Execution plane

The model decides; the backend executes under control

The model outputs plans and structured tool calls; the backend validates arguments, permissions, and call state, then executes retrieval, code, file, or browser tools and writes results back to the context to continue reasoning.

State and messaging

Business facts, process state, and real-time delivery are separated

Structured business data goes to the database; files and final artifacts go to object storage; Redis handles cache and short-term process state; the reliable messaging system handles ordered real-time delivery of long-running task events.

Security and observability

Trust neither model output nor internal network safety

Generated code runs in an isolated sandbox, sensitive data uses user-level encryption, service-to-service communication uses TLS; logs, metrics, and traces span model, tool, messaging, and storage calls.

Why this structure matters: a single Agent run can last minutes and cross multiple external dependencies. The system cannot treat a browser connection or a single service process as the source of task truth; execution progress, messages, and final artifacts must live in recoverable boundaries.

05 · Engineering case 1

Migrating the tool protocol is not replacing a parser.

Tool calling is the main loop of the Agent Runtime: the model proposes a call, the backend validates and executes it, then writes the result back to the context. The old approach relied on the model emitting text in an agreed format, which was prone to format drift; native structured calls are more reliable, but the migration simultaneously touches the message protocol, streaming events, Sub-Agents, and multi-model compatibility.

Use dual-mode to turn a high-risk migration into an observable, reversible evolution

Not a “one-shot switch,” but letting two protocols coexist under control in the same runtime.

Led / primary developer
Problem

Structured calls have different message blocks and streaming events across model SDKs; after the main Agent switches, Sub-Agents, result feedback, and message history must stay on the same protocol.

Approach

Keep the old protocol as fallback and select the running mode by configuration; unify tool definitions so the same tool can be exposed under both protocols; propagate the mode to Sub-Agents and adapt streaming aggregation and result pairing.

Correctness

Validate tool name, call ID, and argument completeness before execution; incomplete streaming calls are forbidden from producing side effects, so truncated JSON cannot pollute the later context.

Release

Runtime metrics record calling mode and failure types; use small-batch enablement, comparison, and fast rollback instead of a one-time full migration.

Engineering judgment

The risk of a protocol migration is not only in the producer, but in all consumers and historical data. The real completion bar is that the main Agent, Sub-Agents, executors, message history, and observability all understand the same protocol version.

06 · Engineering case 2

Keep long-task context controllable, and bring retrieval back with evidence and citations.

Long-running tasks keep producing new tool results and intermediate state; without active management, the context grows without bound. Meanwhile, when knowledge-base information must be cited, retrieval results must be verifiable and traceable rather than generated by the model from memory.

Context control

Pre-statistics, hierarchical compaction, and dynamic loading

Account for token usage before the call and reserve tool state; hierarchical compaction compresses history at key points while deterministically preserving plans and tool execution state; Skills are swapped in and out on demand so irrelevant knowledge does not occupy context.

Agentic RAG

Candidate retrieval → evidence reading → continued search → source citation

Keyword, vector, and semantic ranking retrieve candidates through multiple paths; evidence reading judges relevance; search continues when coverage is insufficient; the answer is delivered with source passages and citations instead of an uncited model summary.

Engineering boundary

Compaction must not break executable state

If context compaction swallows tool results or the task plan, later loops lose execution context. Compaction must preserve protocol invariants and recoverable task state.

Core contribution · context accounting / hierarchical compaction / dynamic Skills / Agentic RAG architecture and development

07 · Engineering case 3

Upgrade “messages exist” to “the real-time channel recovers by itself.”

Long-running Agent tasks last minutes and produce many ordered messages. The old approach kept history in a Redis List but pushed real-time events over Redis Pub/Sub: when a subscriber is briefly offline, messages are not held, and users can only recover by refreshing and reading history.

Persistent process stateRedis List

Holds short-term history, supports replay after refresh and reconnect.

+
Reliable real-time layerService Bus Session

Retains unacknowledged messages, provides ack, redelivery, and per-session FIFO.

Architecture judgment

The problem is delivery semantics, not retry counts

Pub/Sub's broadcast semantics cannot be turned into an offline-retention queue by retrying around it. The fix must redefine who owns real-time reliability.

Migration control

Abstract the transport layer, keep gray rollout and fallback

A unified MessageTransport interface isolates the business layer, so old and new transport implementations can be switched by configuration instead of spreading an infrastructure migration across all callers.

Concurrency pitfall

Resource lifecycles must be isolated by failure boundary

Shared sending resources interfere with each other under concurrency. The fix separately handles per-channel isolation, concurrent creation, locks, and partial eviction-and-rebuild after failures.

Honest boundary

at-least-once is not exactly-once

Queues may redeliver; display messages and side-effecting tool executions still need idempotency keys and state machines at the business layer.

Independently owned · diagnosis / transport abstraction / Service Bus Session / concurrency and recovery

08 · Engineering case 4

Let the Agent be safely integrated by other systems, and protect user data.

A production Agent must both be callable by external products and handle user files and sensitive data. Interface, identity, task state, storage encryption, and transport security must form a continuous boundary rather than isolated features.

A / Agent Proxy

Wrap long-running tasks as recoverable asynchronous APIs

Agent Proxy uses the OBO delegated-authorization chain to access downstream resources on behalf of the user, and wraps long-running tasks as queryable, recoverable asynchronous interfaces; with task state persisted, running tasks can recover after a service restart.

  • Independently designed from zero and delivered to production
  • OBO authorization, task persistence, restart recovery
  • Containerization and CI/CD for independent release and maintenance
B / User Encryption

Design retrieval, key isolation, and rotation together

Stable hashes carry lookup; raw identity and user data are stored encrypted; layered keys limit the blast radius of any single compromise; self-describing ciphertext supports coexistence of old and new keys and progressive migration.

  • Owned the system architecture and protocol design
  • The team onboarded each data layer under a unified contract
  • Sharing scenarios distinguish authorized identity from decryption identity
C / Service TLS

Eliminate plaintext communication between service nodes

Completed certificate injection at runtime, format conversion, server-side HTTPS, client CA validation, and multi-environment migration; the accurate boundary is one-way TLS engineering integration, not implementing the TLS protocol or mTLS.

  • Independently completed engineering integration and deployment migration
  • Keys never enter code or images
  • Retains room to evolve toward stricter service identity verification
09 · Engineering judgment

This work formed four engineering principles.

01

Define delivery semantics before choosing infrastructure

Reliable messaging is not chosen by a simple Redis-versus-Service-Bus performance comparison, but by whether long-running tasks need offline retention, ordering, consumer acknowledgement, and failed redelivery.

02

Keep observability, gray rollout, and fallback for production migrations

Native Function Calling supports old and new protocols through dual-mode; message transport switches implementations through a unified interface. Both migrations kept runtime metrics, phased enablement, and configuration rollback.

03

Model the visitor, the data owner, and the decryption identity separately

In public sharing, a visitor passing the access check does not mean they can use their own key to decrypt the owner's data. The system must first verify access, then decrypt within a controlled scope using the data owner's encryption context.

04

Independent delivery covers development, deployment, and operations

Agent Proxy is not just an API implementation; it includes authentication, task-state persistence, restart recovery, containerization, CI/CD, and observability so it can be deployed and maintained as an independent service.
