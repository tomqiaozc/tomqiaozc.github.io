00 · 项目背景与职责

先看这项工作的定位，再进入机制。

项目背景

面向真实软件交付的 Agent Harness

这项工作的目标不是生成代码片段，而是把真实的产品需求（External Issue）转化为可持久化、可认领、可恢复的 Task，让多个 Agent 在受控状态下协作完成开发与交付。

我的职责

参与建设并规模化落地

负责将实现、独立评审、证据裁决、修复迭代与合并建模为可回退的 DAG；推动任务领取与超时接管、重试及失败恢复保障长任务可靠运行；并将执行证据聚合后写回任务模板、Skill、规则或 Harness，形成持续改进闭环。

系统状态

成为项目需求实现的主要执行路径

建成后，项目需求主要通过该 Harness 执行：开发、评审、验收、合并决策均由证据与状态图驱动，而不是依赖单次模型上下文。

01 · 多 Agent Harness

用状态图组织多个 Agent，而不是把整个工作流塞进一次对话。

真实软件交付跨越实现、评审、验收、修复、合并多个阶段，单个 Agent 的一次上下文装不下整条链路。Harness 把工作组织为以 Task State 为执行主线的有向图，每个 Agent 只处理当前状态的职责，通过持久化状态与 artifacts 跨 run 交接。

Task State

需求变成可持久化、可认领、可恢复的任务

外部 Issue 转化为持久化 Task，记录当前状态、执行归属、claim 和证据；Agent 失败或交接时，系统仍知道任务做到哪里、下一步由谁处理。

角色分工

Developer、Reviewer、Judge 各司其职

Developer 实现需求并提交证据；Reviewer 独立评审；Judge 根据需求与证据裁决是否满足验收。实现者不能批准自己的实现，模型自述不能替代证据。

证据门禁

代码、测试、PR、CI、截图控制状态流转

状态推进由确定性证据驱动：类型检查、测试、架构检查、CI、Review 和桌面/移动端截图共同构成合并决策的依据。

核心设计

DAG把实现、独立评审、证据裁决、修复迭代与合并建模为可回退的有向图；任务领取与超时接管、重试与失败恢复让长任务在无人值守下可靠运行。

02 · 任务生命周期

任务沿显式状态推进，语义判断、系统事实和风险责任由不同角色处理。

人的需求进入任务系统后，不会被简单地“取出并执行”。Task Engine 记录当前状态、执行归属和证据；Developer、Reviewer、Judge 负责不同阶段，CI 与对账程序提供确定性事实，必要时再由人处理例外和风险决策。

03 · 代表性需求示例

为聊天消息增加复制操作，一项普通需求如何走完整个 Loop。

以下使用一个常见前端需求说明 Harness 的工作机制：在 Assistant 消息下增加复制操作，并适配桌面端与移动端。它是机制示例，用于展示各阶段如何协作。

需求不只变成代码，还要形成可核验的交付结果

每一阶段都留下下一位角色可以复核的状态和证据。

REPRESENTATIVE FLOW
Intake

任务说明用户行为、交互位置、桌面与移动端要求，以及复制成功和失败时的反馈方式。

Implement

Developer Agent 定位共享消息组件与设计系统能力，完成实现、测试和必要的状态处理，并提交 PR。

Verify

类型检查、单元测试、lint 和架构规则先验证确定性要求；Reviewer 再检查组件复用、交互行为和边界情况。

Judge

Judge 结合 PR、测试结果和桌面/移动端截图判断验收标准是否满足；证据不足或行为错误则退回修改。

Deliver

所有检查通过后进入待合并状态；只有 GitHub 确认 PR 已合并，内部任务才记录为真实交付。

Improve

如果多个 Surface 重复实现同类操作，团队可以把共享组件约束或检查写回系统，再观察后续任务是否开始复用统一实现。

04 · Loop Engineering 飞轮

聚合执行证据，把改进写回系统，再用后续任务验证。

一次任务的完成不是终点。要持续提升 Harness 与 Agent 的交付质量，需要把多次任务的执行证据聚合起来，识别反复出现的系统性问题，把结论写回任务模板、Skill、规则或测试，再用后续同类任务的执行证据验证改进是否生效。

先有真实交付证据

多次任务的 trace、失败类型、耗时、重试、架构检查与交付证据是 Loop 的输入，而不是模型自述或一次成功案例。

聚合

识别反复出现的系统性问题

把证据按失败类型和根因分类，识别哪些问题反复出现，而不是把每次失败当作孤立事件处理。

写回

把结论写回系统

改进结论写回任务模板、Skill、规则、测试或 Harness，让下一次任务从一开始就遵守新的约束。

验证

用后续任务验证改进

写回只是改进动作；只有后续同类任务的通过率、返工、证据完整性或失败模式发生可验证变化，才能说明 Loop 得到改善。

完整闭环：执行 → 聚合 → 写回 → 再验证。每个环节都要求证据可核验、改进可测量，避免把“修复当前任务”误认为“系统已经改善”。

05 · 工程认识

从 Agent Harness 与 Loop Engineering 中形成的四点认识。

01

自主执行从任务对象化开始

只有把需求变成可持久化、可查询、可认领和可恢复的任务，系统才能管理无人监督的 Agent 工作，而不是依赖一次聊天会话。

02

模型自述不能替代验收证据

确定性测试、架构检查、独立 Review 和可复核产物需要进入执行图，Agent 不能仅凭“任务已完成”推进状态。

03

内部状态不能替代外部交付事实

Task Engine 可以记录执行进度，但 PR、CI 和真实合并状态仍由 GitHub 等外部系统确认，两者需要持续对账。

04

写回改进之后还需要验证

修复当前任务或增加一条 Skill、规则并不代表系统已经改善；后续同类任务的证据和结果变化才是闭环是否有效的判断依据。
