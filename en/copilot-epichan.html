00 · Project background and role

Start with the positioning of this work, then enter the mechanism.

Project background

An Agent Harness for real software delivery

The goal was not to generate code snippets, but to turn real product requirements (external Issues) into persistent, claimable, recoverable Tasks, so multiple Agents collaborate under controlled state to complete development and delivery.

My role

Contributed to building and scaling it

Modeled implementation, independent review, evidence adjudication, repair iteration, and merge as a reversible DAG; drove task claiming with timeout takeover, retries, and failure recovery to keep long-running work reliable; and fed aggregated execution evidence back into task templates, Skills, rules, or the Harness to form a continuous improvement loop.

System status

Became the primary execution path for project requirements

After it was built, project requirements were mainly executed through this Harness: development, review, acceptance, and merge decisions were driven by evidence and the state graph rather than a single model context.

01 · Multi-Agent Harness

Organize multiple Agents with a state graph, not by cramming the whole workflow into one conversation.

Real software delivery spans implementation, review, acceptance, repair, and merge; a single Agent's one-shot context cannot hold the whole chain. The Harness organizes work as a directed graph centered on Task State, where each Agent handles only its current-state responsibility, with persistent state and artifacts carrying work across runs.

Task State

Requirements become persistent, claimable, recoverable tasks

External Issues become persistent Tasks that record current state, execution ownership, claim, and evidence; when an Agent fails or hands off, the system still knows where the task stands and who handles the next step.

Role separation

Developer, Reviewer, and Judge each own a distinct responsibility

The Developer implements and submits evidence; the Reviewer reviews independently; the Judge decides whether acceptance is met against the requirement and evidence. The implementer cannot approve its own work, and model self-reports cannot substitute for evidence.

Evidence gates

Code, tests, PRs, CI, and screenshots govern state transitions

State progression is driven by deterministic evidence: type checks, tests, architecture checks, CI, reviews, and desktop/mobile screenshots together form the basis for merge decisions.

Core design

A DAG models implementation, independent review, evidence adjudication, repair iteration, and merge as a reversible graph; task claiming with timeout takeover, retries, and failure recovery keep long-running work reliable even unattended.

02 · Task lifecycle

Tasks advance along explicit states; semantic judgment, system facts, and risk decisions are handled by different roles.

A human requirement entering the task system is not simply “picked up and executed.” The Task Engine records current state, execution ownership, and evidence; Developer, Reviewer, and Judge handle different phases, CI and reconciliation programs provide deterministic facts, and humans handle exceptions and risk decisions when necessary.

03 · Representative requirement

Adding a copy action to chat messages: how an ordinary requirement moves through the whole Loop.

Below uses a common frontend requirement to show how the Harness works: adding a copy action under Assistant messages, adapted for desktop and mobile. It is a mechanism example showing how each stage collaborates.

A requirement becomes not just code, but a verifiable delivery result

Each stage leaves state and evidence that the next role can re-check.

REPRESENTATIVE FLOW
Intake

The task describes user behavior, interaction location, desktop and mobile requirements, and the feedback on copy success and failure.

Implement

The Developer Agent locates the shared message component and design-system capabilities, completes the implementation, tests, and necessary state handling, and opens a PR.

Verify

Type checks, unit tests, lint, and architecture rules verify deterministic requirements first; the Reviewer then checks component reuse, interaction behavior, and edge cases.

Judge

The Judge determines whether acceptance is met using the PR, test results, and desktop/mobile screenshots; insufficient evidence or wrong behavior sends it back for revision.

Deliver

After all checks pass, the task enters a merge-ready state; only when GitHub confirms the PR is merged does the internal task record real delivery.

Improve

If multiple Surfaces implement the same operation repeatedly, the team can write a shared component constraint or check back into the system, then observe whether later tasks start reusing the unified implementation.

04 · Loop Engineering flywheel

Aggregate execution evidence, write improvements back, then validate them with later tasks.

Completing one task is not the end. To keep improving the delivery quality of the Harness and Agents, execution evidence from many tasks must be aggregated, systemic issues identified, conclusions written back into task templates, Skills, rules, or tests, and then the improvements validated by the execution evidence of later similar tasks.

Execute

Start with real delivery evidence

Traces, failure types, duration, retries, architecture checks, and delivery evidence across tasks are the input to the Loop, not model self-reports or a single success case.

Aggregate

Identify recurring systemic issues

Classify evidence by failure type and root cause to identify which issues recur, rather than treating each failure as an isolated event.

Write back

Feed conclusions back into the system

Improvements are written back into task templates, Skills, rules, tests, or the Harness, so the next task starts observing the new constraints from the beginning.

Validate

Validate improvements with later tasks

Writing back is only an improvement action; the Loop is improved only when the pass rate, rework, evidence completeness, or failure patterns of later similar tasks change verifiably.

The complete loop: execute → aggregate → write back → re-validate. Every stage requires verifiable evidence and measurable improvement, so “fixing the current task” is never mistaken for “the system has improved.”

05 · Engineering principles

Four principles from Agent Harness and Loop Engineering.

01

Autonomous execution starts with making the task an object

Only when a requirement becomes a persistent, queryable, claimable, recoverable task can the system manage unattended Agent work instead of relying on a chat session.

02

Model self-reports cannot replace acceptance evidence

Deterministic tests, architecture checks, independent review, and re-checkable artifacts must enter the execution graph; an Agent cannot advance state merely by saying “task complete.”

03

Internal state cannot replace external delivery facts

The Task Engine can record execution progress, but PR, CI, and real merge state are confirmed by external systems like GitHub; the two must keep reconciling.

04

Writing back an improvement still requires validation

Fixing the current task or adding a Skill or rule does not mean the system has improved; the evidence and outcome changes of later similar tasks are what determine whether the loop is effective.
