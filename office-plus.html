01 · 项目与系统背景

Office Plus 不是一个支付接口，而是一组相互协作的商业化领域。

用户完成付款只是交易事实。平台还要判断活动资格、发放会员或用量权益、调用第三方服务、通知用户，并在账号、合同或外部系统状态变化时继续保持正确。

交易

订单记录资金事实

SKU、预订单、订单、支付、退款和发票描述一次购买发生了什么。

活动

Campaign 编排增长规则

买赠、资格、奖品包和兑奖从订单条件中拆出，避免增长逻辑散落在交易代码里。

权益

用户服务管理资产

会员时长、论文查重字数和兑换权益拥有不同的发放、消耗与回滚规则。

消息

异步任务推进长链路

后台任务与 Service Bus 承接支付回调、检测、续费、通知和失败补偿。

身份

账号与设备控制访问

AuthenticationCenter 管理登录、Token、设备会话、撤销和过期清理。

团队基础

个人工程复用平台能力

支付渠道、权益、活动、消息、Blob 和配置平台由团队共同建设，是下文五项主导工作的基础。

02 · 核心系统约束

订单成功，不等于合同、权益或第三方结果都已成功。

不同领域必须保存自己的状态，再通过幂等、重试与补偿逐步收敛。把所有步骤压进一次同步请求，会让任何外部超时都变成无法判断的“半成功”。

正确性

锁只能削峰，状态与唯一约束负责裁决

回调、消息和定时任务都可能重复执行；业务状态机、唯一键和数据库条件更新共同防止重复扣款或重复发放。

恢复性

每一种失败都有明确的下一步

网络失败、第三方拒绝、结果不一致和任务中断分别进入重试、查询、回滚、退款或补偿，而不是统一吞掉异常。

个人贡献 02 · 微信连续包月

连续包月不是每月跑一次定时任务，而是四类状态的长期一致性。

我主导方案与落地。合同只代表用户授权代扣；首月和每个续费周期仍要创建独立订单、处理支付回调并发放会员权益，才能审计每次金额、支付结果和权益来源。

首月签约与次月续费分开建模

合同、月度订单、支付和会员权益各自保存状态。

端到端主导
首月

短期 PreContract 保存签约上下文；微信签约回调验签后异步落合同，再创建首月订单并发起扣款。扣款成功后才写 Payment、推进订单并 AddVip。

续费

提醒任务负责提前发送站内信，续费任务分页扫描即将到期的 Signed 合同，创建本月 AUTO_RENEWAL 订单后申请扣款。

重复处理

合同号唯一约束、回调验签、RedLock、订单状态机、最近续费订单检查与延迟取消共同处理重复回调和任务重跑。

失败处理

首扣失败会释放优惠券并终止空合同；主动解约和微信删除回调通过独立合同状态推进，不用订单状态代替合同事实。

个人贡献 03 · 账号软删除

把“立即物理删除”改造成可撤销、可审计的账号生命周期。

我主导总体设计、核心开发、跨服务推进和上线。目标既是提高反复删号 / 合并账号获取低价权益的成本，也要给真实用户保留冷静期与恢复路径。

持久化删除意图，再由周期任务完成清理

删除不是一条延迟消息，而是一份可以重新扫描的业务事件。

端到端主导
前置阻塞

存在微信连续包月合同时拒绝删除，要求用户先解约；避免账号消失后微信仍继续扣费。

软删除

账号进入 DELETING，创建唯一删除事件并撤销旧 Refresh Token；重复申请由状态和唯一约束阻止。

恢复

冷静期内重新登录会恢复 ACTIVE、删除事件并清缓存；账号状态是签发新 Token 前的服务端判断。

最终清理

Worker 周期分页扫描到期事件，物理删除前再次核对状态；单条失败不阻塞整批，事件保留到下一轮继续处理。

诚实边界：状态机、唯一事件、到期二次校验、周期补扫与跨服务删除重放已落地；严格的恢复 / 删除互斥、M365 条件的后端复查，以及 Token 撤销失败后的持久化补偿仍可加强。

个人贡献 04 · Token 与设备会话

用 JWT 减少逐 Token 状态，再用设备记录保留可撤销能力。

我主导 Refresh Token 重构、设备会话模型、设备数限制、清理 Worker、压测选型和版本化迁移。核心不是“改成 JWT”，而是决定什么可以无状态，什么仍必须由服务端保存。

01 / 凭据

JWT Refresh Token

Token 携带 WIC、Office Plus 与 Device ID，并由服务端签名；刷新时校验签名、用户 / 设备一致性和有效期。

不再逐 Token 落表
02 / 会话

UserDeviceRecord

设备记录承担撤销、设备数限制和过期状态；记录不存在时，即使 JWT 尚未过期也拒绝刷新。

保留服务端控制
03 / 运维

同步保活，异步清理

刷新请求同步 touch 当前设备；Iterator、Service Bus 与 Cleaner 异步扫描和批量删除过期记录。

在线正确性与维护解耦
≈9K/min设计期 refresh 峰值
21% → 2%压测 CPU 峰值
20m / 33m100 万消息两种消费模式

选型边界：以上是设计阶段实验，用于比较同步写入、异步批处理以及 ReceiveAndDelete / PeekLock，不是生产 SLA。设备清理可由后续扫描补偿，因此接受更高吞吐但可能丢消息的消费方式；支付和权益消息不能套用这一结论。

旧模型：MAU × Devices × 30 级别的长期记录 → 新模型：MAU × Devices 级别的设备状态

个人贡献 05 · 渠道直充

把“请求已受理、VIP 已到账、通知已送达”拆成三个结果。

我主导 Partner 体系、外部 API、安全边界、异步履约、回调补偿、查询与退款闭环。合作方按手机号充值 VIP 时，外部请求不可信、通知网络不可靠，但同一订单绝不能重复发放权益。

受理

同步返回只代表进入系统

校验应用身份、权限、业务签名、SKU、回调地址和重复订单后，创建 INIT 记录并投递消息；此时不能声称 VIP 已到账。

履约

TopupStatus 记录业务结果

Worker 创建订单并调用权益服务；只有本地流程完成后才进入 SUCCESS。合作方订单唯一约束与状态检查防止重复充值。

通知

NotifyStatus 独立保存

通知失败不回滚已经发放的 VIP，也不能重跑充值；合作方可查询真实状态，平台可单独重发通知。

安全

身份、权限与参数完整性分层

Entra 应用身份和 App Role 控制谁能进入 API，Partner Secret 签名保护这次订单参数，HTTPS 负责传输保密。

个人参与 · 会员订单与普通支付

能讲清复杂存量系统，不等于拥有它的原始设计权。

团队既有的普通订单支付体系不是我主导设计的。我在后期参与部分工作，并系统梳理 Growth 服务、SKU 展示、预订单 / 订单、微信与支付宝支付回调、退款和异常补偿；微信连续包月则是独立的主导项目。

交易建模

SKU 与订单不是静态页面数据

展示结果会叠加在售状态、用户类型、历史订单、当前权益 / 签约、活动赠品等条件；临时 PreOrder 与持久化 Order 分开承载不同生命周期。

支付正确性

回调进入后台任务，使用订单锁、状态机和唯一约束防重；超时关单前先查询渠道真实状态，避免回调延迟导致误关单。

退款恢复

资金与权益分别落账并最终收敛

退款申请、渠道异步结果、订单 / 支付更新和 VIP 回收是多个步骤，需要查询、延迟任务和补偿处理。

09 · 工程取舍与边界

这些工作最终形成了四点工程认识。

领域状态

不要用一张表代表整条链路

合同、订单、支付、权益、第三方任务和通知各自保存事实，才能判断失败发生在哪一步。

幂等

锁、状态机和唯一约束各有职责

锁降低并发冲突，状态机限制合法迁移，持久化唯一约束提供最终裁决；不能把一把分布式锁当成全部正确性。

恢复

失败是业务分支，不是日志结尾

重试、查询、回滚、退款、补扫和人工处理需要在设计时明确，并留下可以重新判断的持久化状态。

事实边界

区分已落地、参与和可加强项

连续包月跨实例唯一键、软删除严格互斥等是改进方向；普通支付是后期参与，不能与五项主导混为一谈。
