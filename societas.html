01 · 产品与系统

从一次回答，走向一项工作的完整交付。

用户给出一个真实工作目标，系统拆解任务、调用模型与工具，在隔离环境中处理代码和文件，需要时操作浏览器，检查结果并交付可编辑的文档、演示、分析或网页。成功任务还能被沉淀为后续可复用的能力。

01理解目标

明确交付物、受众和质量标准。

02规划与执行

调度模型、工具、子 Agent、沙箱和浏览器。

03检查与恢复

记录状态，处理失败、重试和断线恢复。

04交付与复用

输出可编辑成果，并沉淀稳定步骤。

系统设计范围：除模型推理外，长任务还会跨越工具、沙箱、消息系统和客户端，因此需要相应的状态恢复、可观测性和执行控制机制。

03 · 简化系统架构

普通 API 接住请求，Agent Runtime 承担不确定的长任务执行。

公开层面可以把 Office Agent 理解为两个不同的运行边界：API 层负责身份、任务入口和状态查询；Agent Runtime 负责模型推理、计划推进、工具执行和产物生成。两者拆开后，可以针对短请求和长任务分别扩缩容、发布和恢复。

用户提交目标
API 创建 Run
Agent 规划 / 调工具
沙箱或浏览器执行
消息推送 / 产物交付
失败或断连 → 保存进度与事件 → 从已确认状态继续 ↺
执行平面

模型负责决策，后端负责受控执行

模型输出计划和结构化工具调用；后端校验参数、权限和调用状态，再执行检索、代码、文件或浏览器工具，并把结果写回上下文继续推理。

状态与消息

业务事实、过程态和实时投递分工

结构化业务数据进入数据库，文件与最终产物进入对象存储；Redis 承担缓存和短期过程态，可靠消息系统负责长任务事件的有序实时传递。

安全与观测

不信任模型输出，也不假设内部网络安全

生成代码在隔离沙箱执行，敏感数据采用用户级加密，服务间通信使用 TLS；日志、指标和 Trace 贯穿模型、工具、消息与存储调用。

为什么这个结构重要：Agent 的一次运行可能持续数分钟，并跨越多个外部依赖。系统不能把浏览器连接或单个服务进程当作任务事实来源，必须把执行进度、消息和最终产物放在可恢复的边界中。

05 · 工程案例一

迁移工具协议，不是替换一个解析器。

工具调用是 Agent Runtime 的主循环：模型提出调用，后端校验并执行，再把结果写回上下文。旧方案依赖模型输出约定格式的文本，容易受格式漂移影响；原生结构化调用更可靠，但迁移会同时触及消息协议、流式事件、子 Agent 和多模型兼容。

用 dual-mode 把高风险迁移变成可观察、可回退的演进

不是“一次切换”，而是让两种协议在同一运行时内受控共存。

主导 / 主力开发
问题

结构化调用在不同模型 SDK 中有不同的消息块和流式事件；主 Agent 切换后，子 Agent、结果回填和历史消息也必须保持同一协议。

方案

保留旧协议作为回退，通过配置选择运行模式；统一工具定义，让同一工具可按两种协议暴露；把模式传递到子 Agent，并适配流式聚合和结果配对。

正确性

执行前验证工具名、调用 ID 和参数完整性；不完整的流式调用禁止产生副作用，避免残缺 JSON 污染后续上下文。

发布

运行指标记录调用模式和失败类型，用小范围启用、对比和快速回退替代一次性全量迁移。

工程判断

协议迁移的风险不只在生产者，还在所有消费者和历史数据。真正的完成标准是：主 Agent、子 Agent、执行器、消息历史和可观测性都理解同一版本的协议。

06 · 工程案例二

让长任务上下文可控，让检索带回证据与引用。

长任务会不断产生新的工具结果和中间状态，若不主动管理，上下文会持续膨胀；同时，需要引用知识库信息时，检索结果必须可验证、可追溯，而不是模型凭印象生成。

上下文控制

预统计、分层压缩与动态加载

调用前统计 Token 用量并预留工具状态；分层 Compact 在关键节点压缩历史而确定性保留任务计划与工具执行状态；Skill 按需换入换出，避免无关知识占据上下文。

Agentic RAG

候选召回 → 证据深读 → 继续检索 → 原文引用

关键词、向量与语义排序多路召回候选，对候选做证据深读判断相关性，不足时继续检索，最终以原文片段和来源引用交付答案，而不是让模型无来源地总结。

工程边界

压缩不破坏可执行状态

上下文压缩如果吞掉工具调用结果或任务计划，后续循环就会丢失执行上下文。压缩必须保留协议不变式和可恢复的任务状态。

核心参与 · 上下文统计 / 分层 Compact / 动态 Skill / Agentic RAG 架构与开发

07 · 工程案例三

把“消息存在”升级为“实时链路会自动恢复”。

Agent 长任务会持续数分钟并生成大量有顺序的消息。旧方案把历史片段保存在 Redis List，但实时推送使用 Redis Pub/Sub：订阅端短暂离线时消息不会等待，用户只能刷新后从历史记录补回。

持久过程态Redis List

保存短期历史，支持刷新和重连后的重放。

+
可靠实时层Service Bus Session

留存未确认消息，提供 ack、重投和同会话 FIFO。

架构判断

问题是交付语义，不是重试次数

Pub/Sub 的广播语义无法通过外围重试变成离线留存队列。修复必须重新定义谁对实时可靠性负责。

迁移控制

抽象传输层，保留灰度和回退

统一 MessageTransport 接口隔离业务层，使新旧传输实现可以按配置切换，而不是把基础设施迁移扩散到所有调用方。

并发踩坑

资源生命周期必须按故障边界隔离

共享发送资源在并发下会互相影响。修复分别处理按通道隔离、并发创建、使用锁和失败后的局部淘汰重建。

诚实边界

at-least-once 不等于 exactly-once

队列可能重复投递，展示消息和有副作用的工具执行仍需在业务层设计幂等键与状态机。

独立负责 · 问题诊断 / 传输抽象 / Service Bus Session / 并发与恢复

08 · 工程案例四

让 Agent 能被其他系统安全接入，也能保护用户数据。

生产 Agent 既要被外部产品调用，又会处理用户文件和敏感数据。接口、身份、任务状态、存储加密和传输安全必须形成连续边界，不能各自成为孤立功能。

A / Agent Proxy

把长任务封装为可恢复的异步接口

Agent Proxy 通过 OBO 授权链路代表用户访问下游资源，并将长任务封装为可查询、可恢复的异步接口；任务状态持久化后，服务重启仍可恢复运行中的任务。

  • 从 0 独立设计并端到端交付至生产
  • OBO 授权、任务持久化与重启恢复
  • 容器化与 CI/CD，支持独立发布和维护
B / User Encryption

把检索、密钥隔离和轮换一起设计

稳定哈希承担查找，原始身份和用户数据加密存储；分层密钥限制单点泄露范围，自描述密文支持新旧密钥并存和渐进迁移。

  • 负责系统架构与协议设计
  • 团队按统一契约接入各数据层
  • 分享场景区分授权身份与解密身份
C / Service TLS

消除服务节点间的明文通信

完成证书运行时注入、格式转换、服务端 HTTPS、客户端 CA 验证和多环境迁移；准确边界是单向 TLS 工程接入，不表述为实现 TLS 协议或 mTLS。

  • 独立完成工程接入与部署迁移
  • 密钥不进入代码和镜像
  • 保留更严格服务身份验证的演进空间
09 · 工程判断

这些工作形成了四点工程认识。

01

先明确交付语义，再选择基础设施

可靠消息的选型依据不是 Redis 与 Service Bus 的简单性能比较，而是长任务是否需要离线留存、顺序保证、消费确认和失败重投。

02

为生产迁移保留观察、灰度和回退机制

Native Function Calling 通过双模式兼容新旧协议；消息传输通过统一接口切换不同实现。两项迁移都保留了运行指标、分批启用和配置回退能力。

03

分开建模访问者、数据所有者和解密身份

在公开分享场景中，访问者通过权限检查，并不意味着可以使用访问者自己的密钥解密所有者的数据。系统需要先验证访问权限，再在受控范围内使用数据所有者的加密上下文完成解密。

04

独立交付覆盖开发、部署和运行

Agent Proxy 不只包含 API 实现，还包括认证、任务状态持久化、重启恢复、容器化、CI/CD 和可观测信息，使其能够作为独立服务部署和维护。
