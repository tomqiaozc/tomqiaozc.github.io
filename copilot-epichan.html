01 · 两个工程环境

Epichan 用真实产品任务验证 Agent-first 开发，Studio 服务大规模生产体验。

二者都是 Microsoft Copilot 下的工程环境，但承担不同角色。Studio 服务多个生产 Surface；Epichan 中的 Bebop Lite 连接真实 Copilot API，同时也是 graph-based Harness 和 Loop Engineering 的验证场。

Epichan · Agent-first Monorepo

产品代码也是 Loop 的测试场

Bebop Lite 提供真实聊天产品环境；共享组件、架构规则、性能检查和 CI 让 Agent 执行面对真实工程约束，而不是只在隔离样例中生成代码。

Studio · Production Frontend

多端共享的 Copilot Web 前端

同一套 React 工程支持不同产品 Surface，共享聊天、设计系统和基础能力，同时由配置控制各端差异。它面对持续发布、兼容性、实验和真实用户流量。

关系

产品前端提供真实需求与质量标准，Graph-based Harness负责一次任务的可靠执行，Loop Engineering连接需求进入、验证交付和经验回流。

02 · Epichan Graph + Loop Engineering

Graph-based Harness 保障一次任务怎样执行，Loop Engineering 管理整条交付链怎样持续改进。

Epichan 不只是另一个 Copilot 前端仓库。Bebop Lite 提供真实产品与验证场；Graph-based Harness 把任务、角色、权限、状态和证据组织为可靠执行内核；Loop 再把需求进入、质量验证、真实交付、反馈写回和后续验证连接起来。

Product Surface

Bebop Lite 提供真实工程环境

Agent 修改的是具有共享组件、架构约束、性能要求和真实后端连接的产品代码，因此结果必须满足正常软件交付标准。

Graph Engineering / Harness

让一次执行可调度、可恢复

任务拥有持久状态、角色、claim、执行记录和检查条件；Agent 失败或交接时，系统仍知道任务做到哪里以及下一步由谁处理。

Loop Engineering

让证据和失败进入下一轮

交付后的 Trace、评测和报告被分类为产品任务、Skill、确定性检查或 Harness 改进，并用后续同类任务验证变化。

03 · 任务生命周期

任务沿显式状态推进，语义判断、系统事实和风险责任由不同角色处理。

人的需求进入任务系统后，不会被简单地“取出并执行”。Task Engine 记录当前状态、执行归属和证据；Developer、Reviewer、Judge 负责不同阶段，CI 与对账程序提供确定性事实，必要时再由人处理例外和风险决策。

04 · 代表性需求示例

为聊天消息增加复制操作，一项普通需求如何走完整个 Loop。

以下使用一个常见前端需求说明 Epichan 的工作机制：在 Assistant 消息下增加复制操作，并适配桌面端与移动端。它是机制示例，用于展示各阶段如何协作。

需求不只变成代码，还要形成可核验的交付结果

每一阶段都留下下一位角色可以复核的状态和证据。

REPRESENTATIVE FLOW
Intake

任务说明用户行为、交互位置、桌面与移动端要求，以及复制成功和失败时的反馈方式。

Implement

Developer Agent 定位共享消息组件与设计系统能力，完成实现、测试和必要的状态处理，并提交 PR。

Verify

类型检查、单元测试、lint 和架构规则先验证确定性要求；Reviewer 再检查组件复用、交互行为和边界情况。

Judge

Judge 结合 PR、测试结果和桌面/移动端截图判断验收标准是否满足；证据不足或行为错误则退回修改。

Deliver

所有检查通过后进入待合并状态；只有 GitHub 确认 PR 已合并，内部任务才记录为真实交付。

Improve

如果多个 Surface 重复实现同类操作，团队可以把共享组件约束或检查写回系统，再观察后续任务是否开始复用统一实现。

05 · 我的 Epichan 工作流

无障碍修复方法从可复用 Skill，演进为 Loop 中的多角色工作流。

在 Studio 中，我先把复现、修复和验证无障碍问题的方法整理为可重复使用的 Agent Skill，并在两个月内关闭 64 个 Sev2 无障碍缺陷，覆盖 6 个 squad。随后，我基于 Epichan graph-based Harness 主导设计并迭代 a11y-remediation-workflow，将复现流程、各角色的证据要求和独立验收沉淀为可复用 Skill；按问题类型验证 ARIA 语义、Accessibility Tree、键盘与焦点行为及跨场景回归，并将重复失败写回 Skill 与回归测试，形成持续改进闭环。

具体的检查规则：我把目标页面、操作步骤和实际读屏表现等复现信息，以及开发、评审、验收各阶段必须提交的证据，写成可重复执行的规则。DOM / ARIA 看似正确但读屏仍异常、键盘导航与预期交互不一致，或共享事件改动导致其他 Surface 回归时，检查直接失败；证据不全，任务不能进入下一阶段。

06 · Copilot 消息编排

一条用户消息会经过会话、编排、模型与工具循环，再以流式事件返回前端。

前端不直接调用一次模型并等待完整文本。页面先取得用户配置与功能开关，再通过长连接发送消息；后端把本轮请求组织为 Turn，由 Orchestrator 选择执行方式，Responder 在模型推理与工具执行之间循环，最终经过安全、引用和格式处理后持续返回结果。

07 · Copilot 生产部署

构建、发布和功能启用是三个可以分别控制的阶段。

Copilot 的生产交付不依赖一次全量切换。前端资源使用内容哈希形成不可变 artifacts；同一批已验证 artifacts 从预生产环境 promote 到生产；区域和用户逐步放量，并通过 Feature Flag 或 Kill Switch 将代码部署与功能启用解耦。

ROLLOUT

用时间控制影响范围

按阶段和区域放量，结合自动检查与健康信号观察变化；出现异常时可以停止后续阶段。

RUNTIME

部署不等于立即启用

Feature Flag 支持实验和逐步开启；Kill Switch 可以在不重新部署的情况下关闭高风险能力。

RECOVERY

恢复路径在发布前准备

回滚、关闭功能或调整区域流量对应不同故障范围，选择依据是异常发生在哪一层，而不是统一重发版本。

08 · 我的 Studio 工程工作

AI Coding 研发效能、生产推理链路与线上保障。

前文说明我对 Copilot 生产推理链路的理解；以下聚焦我实际交付的 CI/CD 吞吐与质量门禁优化，以及参与的多区域渐进发布和线上 on-call。

提升 CI/CD 吞吐并守住质量门禁

面向 AI Coding 带来的高频提交，缩短验证关键路径，同时保留可检查的测试结果与发布门禁。

BUILD TIME ~30% LOWER
CI

推进变更分类与测试并行等构建优化；其中 ConsolidateBundleInfo 与 ImageBuild 并行化由我完成，单项节省约 6 分钟。上述优化将构建时长降低约 30%。

门禁

吞吐优化不降低测试要求；并行任务与产物状态保留可检查的测试结果，只有满足既有质量门禁才进入后续发布阶段。

参与生产渐进发布与线上保障

分阶段观察生产变化，并根据故障所在层次选择停止、关闭或回退方式。

PRODUCTION ROLLOUT
发布

参与 Copilot 多区域渐进发布，通过自动化检查和健康信号观察各阶段变化，避免一次性扩大影响范围。

控制

根据异常发生在代码、功能启用还是区域流量层，使用 Feature Flag、Kill Switch、回滚或流量调整控制影响。

止损

结合发布记录、健康信号和区域状态定位异常来源，并按故障层次停止后续放量、关闭功能、回滚或调整流量。

补充工作 · Flaky Test

把测试噪声变成有状态的治理对象

设计并交付自动检测—隔离—追踪机制：从历史失败和受控复跑识别不稳定测试，确认后隔离并保留记录，修复验证后恢复，使隔离不会退化为永久跳过。

09 · 工程认识

从生产 AI 产品与 Agentic Loop 中形成的四点认识。

01

自主执行从任务对象化开始

只有把需求变成可持久化、可查询、可认领和可恢复的任务，系统才能管理无人监督的 Agent 工作，而不是依赖一次聊天会话。

02

模型自述不能替代验收证据

确定性测试、架构检查、独立 Review 和可复核产物需要进入执行图，Agent 不能仅凭“任务已完成”推进状态。

03

内部状态不能替代外部交付事实

Task Engine 可以记录执行进度，但 PR、CI 和真实合并状态仍由 GitHub 等外部系统确认，两者需要持续对账。

04

写回改进之后还需要验证

修复当前任务或增加一条 Skill、规则并不代表系统已经改善；后续同类任务的证据和结果变化才是闭环是否有效的判断依据。
