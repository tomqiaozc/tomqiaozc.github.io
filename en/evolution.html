01

Mostly writing code by hand

Direct implementation
VS CodeManual + autocomplete

Before AI coding tools became common, I wrote and verified code directly in the IDE, and development work was mostly done by a human.

02

Generating code snippets with AI

Direct implementation
ChatGPTCopilot completionVS Code

I first generated function snippets in chat and copied them back into the project, then used editor completion for simpler needs. AI provided snippets; I integrated, modified, and verified them.

Problem: repeatedly copying between chat, editor, and project was costly

03

Using a coding Agent CLI

Orchestrate execution · serial
OpenCodeCoding CLI

The work entry point moved to the terminal. A coding Agent could read the repo, modify files, and run checks, and I began focusing on describing tasks and accepting results.

04

Letting one Agent take a whole task

Orchestrate execution · serial
Claude Code

The Agent could complete more implementation and verification steps, but the flow was still “assign task → wait → human checks,” and usually only one task advanced at a time.

Next: split independent tasks and run them in parallel

05

Running multiple tasks in parallel

Orchestrate execution · parallel
Isolated workspacesParallel Agents

I split work into independently acceptable tasks and ran them in parallel in isolated workspaces. My focus shifted to dependency management, conflict control, and unified acceptance.

06

Adding memory, independent review, and quality checks

Orchestrate execution → design workflows
Searchable memoryIndependent Agent reviewQuality checks

Parallel execution surfaced two problems: new Agents did not know past experience and repeated mistakes, and the same Agent implementing and reviewing missed issues. I started saving searchable experience and arranging review by an Agent not involved in the implementation.

Next: put these rules into a unified execution flow

07

Organizing multiple Agents with a unified workflow

Design workflows · Agent Harness
Agent HarnessTask State / state graphEvidence gates

This workflow is also called a Harness: persistent Task State is the execution spine, and a state graph drives Developer, Reviewer, and Judge through implementation, review, and acceptance, with code, tests, PRs, CI, and screenshots governing state transitions. Implementation, tests, and independent review advance along explicit states with a record; on check failure the work can roll back or re-run, and only after acceptance does it move to delivery.

Today I no longer do all the implementation myself, but I still need to understand the code, re-check key changes, and own the final acceptance. My main work has become splitting tasks, defining execution rules, arranging independent Agent reviews, and taking responsibility for the final result.$ Focus: direct implementation → orchestrate execution → design workflows and reviews
